Collects live production data (OEE, downtime, faults) from the shop floor and brings work orders, maintenance, stock, quality, safety, HR and commercial modules into one control room. Every factory lives isolated in its own database schema; modules are licensed one by one.

The problem

In a mid-sized metal factory, production data lives on paper next to the machine, maintenance in a spreadsheet, stock in the ERP and quality in another file. An operator sees a fault only when someone reports it; a manager joins four tables to answer “why did OEE drop this week?”. FabrikaOS collapses this into one product: data flows in from the floor by itself, every module sees the same data, and decisions are made from one screen.

What it does

  • Live OEE from the floor. An edge agent (simulator + OPC-UA/Modbus skeleton) sends measurements over MQTT and stores-and-forwards when the link drops. A cloud worker writes each reading idempotently into the right factory’s schema; the dashboard updates over WebSocket with no manual entry.
  • Structural barrier against data leaks. Every factory lives in its own PostgreSQL schema, and the schema context is reset before a connection returns to the pool. A dedicated test family guards the rule.
  • Production to shipment. Work-order state machine and bill of materials: closing a production order consumes the BOM from stock automatically. Lots trace backwards and forwards.
  • Modules: maintenance planning, shifts/downtime + Pareto, stock + multi-line purchase approval (requesters cannot approve), quality + 6-step CAPA, energy (TimescaleDB), safety risk matrix, HR, CRM, contracts, versioned documents.
  • Intelligence layer. Predictive maintenance risk, anomaly scans, OEE horizon forecast and stock-out forecast; models stored as versioned artefacts.
  • SaaS skeleton and enterprise security. Four plans × module entitlements, seat limits, a platform admin on a separate identity plane, signed webhooks, TOTP 2FA, OIDC SSO, an immutable audit log, self-service GDPR-style export and anonymisation.

How it was built with AI

172 of 173 commits are co-authored with Claude. The model provided the speed; the process made the product solid:

  1. 1Spec first, code second. An 8-phase / 33-sprint roadmap, a design document and step-by-step plan per sprint, 24 ADRs. Before the model wrote anything, what and why were on record; implemented test-first.
  2. 2“If this is wrong, data leaks” rules are locked by tests. Seven protected test families cover tenant isolation, provisioning, segregation of duties, OEE maths, AI output, migrations and deletion order. A contract test breaks if a shareable URL is ever added to a data-export artefact: the security decision is guarded by code, not memory.
  3. 3Model output was reviewed. End-of-sprint reviews found real bugs: an SSRF prefix trick in webhook URLs, a permission-restoration flaw, a deletion-order issue. Each closed in its own commit.

September 2026 audit

The product was run and inspected screen by screen. CI had been red for two months (tests were hitting a real object store); every visit to the anomaly screen sent a fresh notification to every manager; unexpected errors surfaced in the browser as “CORS error”; the WebSocket token leaked into logs; every page overflowed horizontally on mobile; notification and webhook workers were missing from deployment; demo data “aged” within days. Each finding was measured, fixed and, where possible, locked with a regression test.

Design

A “control room”: neutral anthracite, blue only for actions, colour only for status. Each menu section carries a line colour borrowed from industrial pipe colour codes, shown as a small signal in the page title, the menu group and the KPI icon. Numbers are set in tabular mono so columns align. Status is never conveyed by colour alone.

Honest limits

What this project does not do, or has not proven yet.

  • A product development study with no live customer; no hosted demo, private repository.
  • GA operations sprints (observability, disaster recovery, UAT) and the supply-chain module were not built.
  • Real PLC integration on the edge is a skeleton; tests use a simulator.
  • Playwright end-to-end tests are not in CI (they need a running stack).
