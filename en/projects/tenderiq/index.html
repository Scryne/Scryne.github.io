Reads Turkish tender specifications and extracts requirements, required documents, risky clauses, deadlines and the bidder’s eligibility gaps. Every finding is highlighted on the original PDF with document, page and clause. A finding that cannot be tied to a source is never shown.

The problem

A bid team reading a 300-page tender is looking for one answer: “Which clause here disqualifies us or puts us at risk, and exactly where is it written?” A general-purpose chat model answers fluently but cannot show the clause it relied on. For a decision with legal consequences, “the model said so” is not enough. The team wants to see the clause with their own eyes.

What it does

  • Hybrid parsing: digital PDF, scanned PDF, DOCX and XLSX. Each page is classified as digital or scanned; scanned pages go to OCR.
  • Grounded extraction: five specialist agents (requirements, documents, risk, timeline, eligibility) run in one LangGraph flow. Every finding must be grounded in a source passage. Ungrounded findings never reach the report, and that rule lives in code, not in the prompt.
  • Hybrid retrieval: dense vectors (BGE-M3) + BM25, RRF fusion and reranking.
  • Human in the loop: every finding is approved, corrected or rejected, with bulk actions, comments and change history. Every decision is reversible and written to an audit trail. Approved findings export to Word and Excel with their source references.
  • Eligibility: the company’s capability profile (certificates, references) is matched against the tender. On the demo tender it correctly flags the missing ISO 27001.
  • SaaS layer: row-level tenant isolation (PostgreSQL RLS), organisations, invites, roles, plans and quotas. A per-tenant LLM budget cap uses Redis reservations and holds under concurrent requests. Designed for Turkish data-protection law: uploaded documents are never used for training.

The struck-through value is what was found, the one beside it what was measured after the fix. Every number comes from the project’s own record.

How it was built with AI

TenderIQ was built by one developer pairing with Claude Code. The skill here is balancing the model’s speed with durable contracts and measurement:

  1. 1Rules in code, memory in files. CLAUDE.md holds binding rules and DURUM.md is every session’s entry point (durable facts, traps, unverified assumptions). Every architectural choice is an ADR. The model does not rebuild context each session; it reads it from the record.
  2. 2AI quality is a CI gate. A golden-set evaluation blocks CI whenever a prompt or model changes. Not “looks better”, but a result measured on the same set.
  3. 3Design contract and visual loop. DESIGN.md defines the brief, the token system and the anti-template rules. Every UI task is captured with Playwright at four screen widths and checked.
  4. 4Model choice by measurement. In September 2026 the development model was retired by its provider (410 Gone). Five candidates were tried; the successor was the one that returned 4/4 findings with verbatim quotes on the test tender.

September 2026 audit

Re-measured before writing the CV, the tests were green locally but the product did not work. The AI pipeline was dead (its model had been retired), CI had been red for a month (2 critical + 6 high vulnerabilities), one empty setting meant six test files were never collected, and a raw “Failed to fetch” leaked to users in ten places. All closed: CI 9/9 green, 0 high/critical in trivy, 18 of 18 routes at 100 for accessibility, and an end-to-end run on a fictional tender producing 34 cited findings.

Takeaway

“Tests pass” and “the product works” are separate measurements. Any system that depends on an external model dies quietly when that model is retired. What catches it is not a unit test but an end-to-end run on a real document.

Honest limits

What this project does not do, or has not proven yet.

  • No hosted demo; the product is ready for closed beta but has no customers yet.
  • Live billing and legal terms are not wired up yet.
