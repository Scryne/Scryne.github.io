Verifies a client company’s identity, screens the company and its directors against sanctions, PEP and asset-freeze lists on a self-hosted engine, records the analyst’s decision with its rationale, and produces an audit-ready, source-linked case file.

The problem

Firms covered by Turkey’s financial crimes regulator (the first target is accounting and audit practices) must screen every new corporate client and its directors against sanctions, PEP and asset-freeze lists before onboarding, and be able to defend that decision in an audit. Today it is manual: names are searched on list websites and screenshots dropped into folders. Turkish spelling differences (“A.Ş.” vs “Anonim Şirketi”, İ/ı) make real matches slip through, and the answer to “why did you dismiss this?” is rarely on record.

What it does

  • Entity register: company, directors, beneficial owners and ownership shares, each value with its source and observation time. National ID numbers sit in an encrypted column; duplicate checks use a keyed blind index.
  • Extraction from documents: upload a signature circular or registry document, Docling turns it into text, and rule-based extraction offers directors and ID numbers as suggestions. Nothing enters the register without approval.
  • Screening: the company and related people are screened against a self-hosted OpenSanctions engine; personal data never leaves. Scores fall into three bands: auto-dismissal (stored with its reason), human review and urgent flag.
  • Decision: the analyst sees each candidate with score, match reasons and source link, then confirms or dismisses with a written rationale. Decisions can be reversed, never deleted.
  • Case file: identity, screenings, decisions, inconsistencies and sources in one PDF/Word file, sealed with SHA-256 and bound to a retention period.
  • Audit trail: every risk-relevant action goes to an append-only, hash-chained log that is re-verified on every view.

How it was built with AI

The code was written with Claude Code, epic by epic (E1.1 → E1.5). What makes it trustworthy is that every compliance promise is a test gate, not a sentence:

  1. 1Tenant isolation is proven, not assumed. Two tenants, every endpoint, under the application role, with direct SQL: zero leakage or the merge is blocked.
  2. 2A false negative is the most dangerous bug. A Turkish evaluation set must hit 100% recall through the real screening engine. If the engine is unreachable, the result shows “NO result”, never “clear”.
  3. 3Decisions are written down and revisable. 8 ADRs and numbered revisions: verification without depending on the trade registry, pulling Docling forward, removing pgvector. The model read what was done and why from the same record every session.
  4. 4The product was run end to end for the first time. A real run surfaced what tests could not: when Docling merged lines into a paragraph, extraction attached the first director’s ID to the second; the suggestion payload stored IDs unencrypted; a failed extraction could never be retried; a dismissed candidate kept a screening in “urgent” forever; a production dependency carried an unauthenticated RCE, and the CI security step could never fail.

Each was measured, fixed and locked with a regression test.

Design

A light, calm workspace. Colour carries risk state only: red for a confirmed match or a screening that could not run, amber for pending review or stale data, green for no match above threshold. Each screen shows the result first, then the rationale, then the action. Every value an auditor compares character by character (ID, score, hash) is set in monospace.

Honest limits

What this project does not do, or has not proven yet.

  • Pre-pilot; no production deployment, private repository.
  • The demo runs against an evaluation index of 34 fictional reference entities. The production catalogue will be connected at deployment.
  • The Docling PDF path was validated with generated documents; real pilot documents are still needed.
